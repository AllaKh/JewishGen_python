## Правила работы с git

- **Никогда не делай `git add -A` или `git add .`** — только конкретные файлы.
- **Перед коммитом** убедись что файл действительно содержит нужные изменения.
- **Revert — опасная операция**: `git revert HEAD` откатывает к последнему _закоммиченному_ состоянию, а не к тому что было в working copy до твоего коммита. Если до твоего коммита были незакоммиченные изменения пользователя — они войдут в твой коммит. Revert их сотрёт. В таком случае нужно делать `git revert HEAD` (revert of revert), чтобы вернуться к своему коммиту, а потом точечно откатить только свои правки.
- **Коммить только то, что просит пользователь.** Не коммить сам по себе.

## FamilySearch — алгоритм скрапера (строго соблюдать)

1. Открыть домашнюю страницу → заполнить First Names, Last Names (+ Place, Birth Year) → SEARCH.
2. Нажать таб Historical Records `[data-testid="hr-tab"]`. URL → `?tab=records`.
3. **Логин НЕ нужен** для показа строк таблицы HR tab. Строки видны без логина.
4. Собрать строки таблицы `tbody tr` МОЖНО без логина. Если 0 строк — увеличивать таймауты ожидания (XHR грузится медленно), логин тут не поможет.
5. **ВХОДИТЬ ОДИН РАЗ ДО открытия записей** — `_sign_in_if_needed` (кнопка nav `[data-testid="no-loggedin-sign-in-button"]`) сразу после HR-таба. С персистентным профилем на 2-м прогоне кнопки нет → пропуск. **БАГ, который я ловил**: полагаться только на ленивый логин «при открытии первой записи» → запись №1 = страница «Sign In» (тайминг редиректа), и этот сломанный стейт каскадом валит Advanced Search (кнопка попапа не находится) → супруга не вводится → 12 однофамильцев вместо 1.
6. `_sign_in_if_needed` ставит `logged_in_ref[0]=True` ТОЛЬКО при реальном входе (ложное «уже залогинен» не должно блокировать вход `_scrape_page` на записи №1).
7. Резерв: если ранний вход не сработал — `_scrape_page` логинится на первой записи (`"login" in url` ИЛИ `"sign in" in title`). После — `logged_in_ref[0]=True`, повторный логин не делать.
8. Все записи открывать на **одной** странице (`page.goto(url)`), не в новых вкладках; после каждой — назад на `results_url`.
9. **Advanced Search — ДО скрапинга, на залогиненной странице результатов** (reload → HR tab → попап `[data-testid="advanced-search-form-button"]` (ждать 10с) → заполнить поля/супругу → Search → заново собрать). **НЕ «после первой записи»** — там стейт сломан логином, кнопка попапа таймаутит. Advanced сужает выдачу (супруга → 1 запись) ДО скрапинга, не скрапим 12 лишних.
10. После Advanced форма пересобирает URL — заново дописать exact имени/фамилии/места (`_apply_exact`).

## FamilySearch — скачивание JPG

- **`expect_download` должен оборачивать ВЕСЬ блок**: первый клик на download кнопку + выбор JPG Only + клик confirm. Иначе если первый клик сам инициирует загрузку — событие пропускается.
- После клика на картинку — ждать `button[aria-label*="Download" i]` до 8 секунд перед тем как пробовать fallback-селекторы. После логина viewer грузится медленнее.
- Записи с `view=index` в URL — индексные, без изображения документа. Не вызывать `_download_jpg`, только сохранить thumbnail.
- Если `_best_img(page)` вернул пустую строку — не вызывать `_download_jpg` вообще.
- Таймаут `expect_download` — 45 секунд.
- Fallback если timeout: ждать 15 секунд появления файла в папке Downloads.

## FamilySearch — логин

- Форма: `#userName`, `#password`, `#login`
- Заполнять через `page.fill()` с retry до 3 раз (React-форма может сбрасывать значение)
- Ждать 2 секунды после появления `#userName` перед заполнением
- После `#login` — ждать редирект на `familysearch.org` без `login` в URL (таймаут 30 сек)
- **Персистентный профиль `.fs_profile`** (`launch_persistent_context`, как у MyHeritage) — логин/куки хранятся между прогонами, входим ОДИН раз, не каждый запуск («запоминай куки»). Первый прогон с пустым профилем всё равно требует ОДНОГО входа (профиль скрапера ≠ обычный Chrome пользователя). Снимать `Singleton*`-локи перед запуском; закрывать лишние восстановленные вкладки. `browser = ctx`, закрытие — `ctx.close()`. Профиль в `.gitignore`.

## FamilySearch — точное совпадение и год (per-field exact)

- **В GUI у КАЖДОГО базового поля свой чекбокс «Exact»**: имя, фамилия, место, год — все передаются и учитываются. Payload: `exact={name,surname,place,year}`.
- **Год — диапазон ±2 по умолчанию** (`_year_range(year, span=2)`): «1897» → `q.birthLikeDate.from=1895&to=1899`, чтобы записи 1898 (переписи) тоже попадали. Чекбокс «Exact» у года → `span=0` (`from=to=year`). **Урок**: точный 1897 ВЫКИДЫВАЛ нужные переписи 1898 — пользователь злилась «что угодно, только не эти три записи». Диапазон лечит.
- **Exact для имени/фамилии/места — добавлять `.exact=on` к тому `q.*`-параметру, который FS САМ положил в URL результатов** (`_apply_exact`, читает реальные `q.givenName`/`q.surname`/`q.anyPlace`/`*Place*` из URL), НЕ выдумывать имена полей. Год-фильтр (`birthLikeDate`) из place-exact исключать.
- `_search`, `_ensure_year_in_url` принимают `exact`; год+exact дописываются в URL одним `goto`. `_ensure_year_in_url` зовётся после HR-таба и после Advanced reload (они сбрасывают URL).

## FamilySearch — слипшиеся родственники в результатах

- Ячейку результатов (`evts`, `rels`) читать через **`innerText`**, НЕ `text_content()` — иначе роль и имя склеиваются: «SpouseRebecca M Sanders». `innerText` держит переносы строк FS.
- Подстраховка `_split_rels` (на случай инлайн-рендера): вставляет `\n` перед каждой ролью и `: ` после («SpouseRebecca M Sanders» → «Spouse: Rebecca M Sanders», каждый родственник на своей строке). Роли — английские (FS у пользователя английский), для других языков best-effort.
- В Word значение пишется через `set_cell_lines` (`docx_util.py`) — разбивает по `\n` и после года-склейки.

## Что НЕЛЬЗЯ делать

- **Логин — ОДИН раз ДО открытия записей** (`_sign_in_if_needed` после HR-таба), НЕ полагаться только на ленивый логин при первой записи (он флакует → запись №1 = «Sign In» → ломается Advanced Search). Собирать строки `tbody tr` можно и без логина (но мы всё равно входим до скрапинга).
- **НЕ запускать Advanced Search «после первой записи»** — только ДО скрапинга, на залогиненной странице (иначе кнопка попапа таймаутит, супруга не вводится).
- **НЕ использовать `.first` для полей семейных членов** — после раскрытия секции Spouse появляются новые поля с такими же плейсхолдерами как у предка. `.first` заполнит поля предка, а не супруга. Использовать `data-testid`.
- **НЕ использовать `button:has-text("Search")` для кнопки в попапе Advanced Search** — это может совпасть с другими кнопками. Использовать `[data-testid="search-button"]`.
- **НЕ делать поспешных выводов** о причине ошибки. "Строк: 0" — скорее всего медленный XHR, а не проблема с логином.

### FamilySearch microfilm viewer — ПРАВИЛЬНЫЙ алгоритм

**Главный урок**: НЕ заполнять input-поле (кириллический селектор ненадёжен).  
Использовать URL-параметр `?i=N` (0-based индекс):
- Снимок 61 → `?i=60`
- Снимок 218 → `?i=217`

```python
base_url = fs_url.split("?")[0]
target_url = f"{base_url}?i={img_num - 1}"
```

**После навигации на `?i=N`:**
- Ждём до 30с появления `img[src]` count > 5 (признак загрузки сетки)
- Если логин → заходим → FamilySearch редиректит обратно на `?i=N` через `state=` параметр
- Если редирект потерял `?i=` → навигируемся вручную на `target_url`
- Thumbnail N уже подсвечен синим → кликаем его → скачиваем

**Браузер для FHL**: отдельный (`async with async_playwright()`) с теми же флагами что FamilySearch scraper:
```python
args=["--start-maximized", "--disable-blink-features=AutomationControlled"]
no_viewport=True, accept_downloads=True
```
Если использовать JewishGen-контекст → FamilySearch выдаёт "Access Denied / Error 15".

## АИС Скарб (skarb_scraper.py + gui/skarb.py)

Сайт `https://archiveskarb.by/db/`. **Логина нет.**

- **Параметр поиска: `q`** (НЕ `ФИО`!). HTML: `<input type="text" name="q">`. Поиск нескольких фамилий через ` или `.
- **Ссылки записей**: `a[href*="ELEMENT_ID"]` (формат `/db/?ELEMENT_ID=275117`). Собирать через JS — надёжнее, чем `query_selector_all`.
- **Пагинация**: `a.modern-page-next` (текст «След.»). Брать href через JS, ходить по всем страницам.
- **Имя персоны**: из текста ссылки в результатах поиска (`row["name"]`), НЕ из `<h1>` страницы записи — там «АИС Скарб» (шапка сайта).
- **Поля записи**: JS-экстрактор пар «Метка: значение» (dl/dt-dd, таблицы, `<b>метка</b> значение`, текстовые строки).
- **Word/Excel**: ссылка-источник в КОНЦЕ записи; в Excel колонки `#, Имя, <поля>, Фото, URL`.

## MyHeritage (myheritage_scraper.py + gui/myheritage.py) — самый сложный

### Антибот: ТОЛЬКО персистентный профиль
- `launch_persistent_context(MH_PROFILE_DIR=".mh_profile")` — НЕ свежий контекст!
- Свежий контекст без cookies → MyHeritage флагует логин как suspicious и шлёт challenge-письмо «Confirm a login attempt».
- После первого успешного входа сессия запоминается, 2FA больше не спрашивает.
- Персистентный профиль **восстанавливает старые вкладки** при старте — закрывать все кроме одной.
- **НЕ хардкодить `user_agent`!** Был прибит `Chrome/124`, а Playwright обновил Chromium до 141+ → UA заявляет 124, а движок отдаёт API 141 → **классический бот-тэлл** («он видит, что ты скрипт»). Headed-Chromium и так отдаёт корректный совпадающий `Chrome/<ver>` (без «Headless»). Анти-детект: `--disable-blink-features=AutomationControlled` (уже делает `navigator.webdriver=false`) + init-script (webdriver/plugins/languages/chrome). **Диагностики гонять НЕ на `.mh_profile`** или с теми же флагами — headless без init-script показывает `webdriver=true` и пачкает репутацию профиля.
- **Куки-баннер — кликать ТОЛЬКО явный accept**: текст «Принять все»/«Accept all» по ВСЕМ фреймам, потом accept-специфичные селекторы (OneTrust). НЕ «первая кнопка в `[class*=cookie]`» — там бывает футер-ссылка/«Отклонить», клик по ней **ломает форму логина**.

### 2FA по почте (КЛЮЧЕВЫЕ уроки)
- MyHeritage шлёт **ДВА письма с РАЗНЫМИ кодами**:
  - **B** «Ваш код подтверждения для входа / verification code» — это код для поля «Введите верификационный код» (приоритет!)
  - **A** «Confirm a login attempt» (анти-фрод, flagged as suspicious) — запасной
  - Читать ОБА, пробовать B потом A.
- Чтение кода — **браузером, новой вкладкой** `mail.yandex.ru` (поле «Mail password» в GUI = пароль того же ящика, что логин MH):
  0. **СНАЧАЛА проверить, не залогинен ли уже** (`_mail_logged_in`): персистентный профиль почти всегда помнит сессию Яндекса → инбокс открывается сразу, **формы входа НЕТ**. Признак: НЕТ `#header-login-button` + есть кнопка «Написать»/строки писем/`#inbox` в URL. Если залогинен — **ВЕСЬ вход пропустить**. **БАГ, который я уже ловил**: гнать логин-цепочку при залогиненной почте → код кликает случайную ссылку `a:has-text("Войти")` (в рекламе/футере!), уходит с инбокса → поле логина не находит → вкладка ломается («Target page closed»), почта «не открывается».
  1. (если НЕ залогинен) `#header-login-button` («Войти»)
  2. `input[autocomplete="username"]` → email
  3. `button[data-testid="add-user-next"]` (Next)
  4. span «Log in with your password»
  5. `input[autocomplete="current-password"]` → пароль
  6. **Код берётся ИЗ СТРОКИ ПИСЬМА В СПИСКЕ (заголовок+превью), письмо НЕ открывается** — так оно и работало. `_scan_codes`.
  7. **САМОЕ ВАЖНОЕ — матчить ЦЕЛУЮ СТРОКУ письма, а не обрывки.** Код `253003` лежит в **превью**, а фраза «код подтверждения для входа» — в **теме**. С широкими селекторами `a, li, div` они попадают в РАЗНЫЕ элементы → ни один не совпадает и с фразой, и с кодом → **0**. **БАГ, который я уже допускал.** Брать контейнер всей строки: `[class*=MessageSnippet i], .mail-MessageSnippet, [data-test-id=message-snippet], li[data-id], a[href*="#message"]` — у него `textContent` = тема+превью. Fallback: письмо MyHeritage с `\b\d{6}\b` без явной фразы = код «B».
  8. Письма на **языке аккаунта** (у пользователя русские: «...на странице входа в MyHeritage: 253003»), не английские — регулярки держать многоязычными. NB: превью пишет «код подтверждения**, который**…» (без «для входа»!), поэтому фразу искать как `подтверждения для входа` по ВСЕЙ строке (тема даёт «для входа»), не привязываться к превью.
  9. `_open_and_read` (открыть письмо, читать из тела) — оставлен ТОЛЬКО как крайний резерв, если скан строки совсем не дал кода. В норме НЕ срабатывает.
- Перед вводом кода: `page.bring_to_front()` (вкладка почты была в фокусе, иначе ввод уходит «в никуда»).
- Кнопка подтверждения называется **«Отправить»** (НЕ «Авторизация» — это фоновая кнопка формы логина!). Искать внутри **модалки с полем кода** (поднять от поля кода к `[role=dialog]`/`.modal`/`form`, кликнуть кнопку внутри).
- **ОДИН** submit! Enter + клик одновременно → MyHeritage делает resend (новый код), старый аннулируется → пустые поля + таймер. Проверять результат до 18с, не отправлять повторно.
- **БАГ (co.il): автозакрыватель вкладок убивал почту.** `_on_new_page` (закрывает junk/facebook/blank-вкладки) закрывал и вкладку `mail.yandex.ru`, которую скрапер сам открывает для 2FA — через ~3с «не myheritage → закрыть». На `.com` (RU/EN/HE) куки уже есть → 2FA не нужен → баг невидим. На **`.co.il` куки НЕ распространяются** (другой домен) → нужен свежий вход + код → почта закрывалась → авторизация падала. **Фикс**: `_browser_read_yandex_code` ставит `ctx._mh_pause_autoclose=True` + `page._mh_protected=True` (снимает флаг в `finally`), а `_on_new_page` их уважает и не трогает вкладки `yandex`/`passport`/`mail`/`outlook`.

### После логина

### Дерево «Архів:Єврейське містечко»
- Корень → **регионы = `== H2 ==` заголовки** корневой страницы (`_live_regions`, читается вживую). **14 регионов**, не 12: у некоторых (**Брацлавське воєводство**, **Переписи різних місцевостей**) НЕТ подстраницы — документы лежат прямо в секции корня (`_region_wikitext` → подстраница ИЛИ `_section_slice` корня). «Примітки» (сноски) исключить.
- В странице региона документы — **ДВА типа ссылок**: прямые `[[c:File:...|label]]` (≈317 на Волынь) И **индексные страницы** `[[Архів:CODE]]` (≈13, напр. `Архів:ЦДАВО/1854/1/136`). У индексной файл спрятан в шаблоне `{{Архіви/справа | link_commons = File:...}}` → `_index_to_file` (regex `link_commons\s*=\s*File:`). **Парсить ОБА** (иначе теряешь ~13 док/регион — БАГ, который я ловил).

### Скачивание — по md5-пути, без API-вызова
- Полный PDF: `upload.wikimedia.org/wikipedia/commons/{h0}/{h0h1}/{quote(fn)}`, где `h=md5(fn.replace(' ','_'))`. Проверено: совпадает с «Full resolution». Так обхожу весь ручной танец «Download all sizes → Full resolution / клик по обложке дважды → ждать рендер PDF».
- Превью (обложка JPG): imageinfo `iiurlwidth` (произвольная ширина рендерится по запросу; конструировать `page1-Npx-thumbnail` нельзя — 400 на не-разрешённой ширине).
- **Перемещённый файл** (404 без редиректа, напр. дублированный префикс `ДАЧгО ДАЧгО-...`): читать **move-log** `list=logevents&letype=move&letitle=File:OLD` → `params.target_title` = новое имя, качать его.

### HTTP 429 — Wikimedia режет массовые скачивания больших файлов (PDF ½–1.3 ГБ!)
- «Зависание» = пауза анти-429, не баг. Лечение: вежливый **мин. интервал между скачиваниями, растущий после каждого 429** (`_dl_gap`), **backoff с уважением `Retry-After`** (не сдаваться, а ждать и повторять), **resume** — если файл уже на диске (>10 КБ), пропускать (не качать заново 500 МБ).

### Перевод запроса (КРИТИЧНО — пользователь вводит RU/EN, сайт украинский)
- Место (повіт/місто) вводится по-русски или по-английски → матчить против украинских секций через **транслитерацию** (`_translit`: и/і/ї/й/ы/y→i, ц/ts→c, х/kh→h, …) + **стем-матч** (первые 6 букв, чтобы пройти склонения: «Сураж»→«Суражського», «Сосниця»→«Сосницького»). Проверено: `Surazh`=`Сураж`, `Sosnitsa`=`Сосниця`.
- Регионы/типы документов — словари `REGIONS`/`DOC_TYPE_TR` (uk→(en,ru)); ключ всегда украинский (для API), показ — двуязычный.

### Поиск — ТОЛЬКО через URL (домашняя форма ненадёжна)
- `#firstName/#lastName/#birthYear` на главной **НЕ находились** (форма меняется) → строю URL и `goto`, форму не заполняю.
- **URL** (сверено с целевым URL пользователя): `/search/?name=First+Middle_Last&birth=YEAR&birth_x=<N>-0-0&residence=PLACE&father/mother/spouse/sibling/child=First_Last&keyword=…&gender=m|f&race=…&count=50`.

  - **Год = диапазон `birth_x=<N>-0-0`**, N = ±лет (0 = точный год). Подтверждено: «+/-1 yr» → `birth_x=1-0-0`. В GUI — выпадашка как в MH (Exact/±1/±2/±5/±10), N передаётся `year_range`. БЕЗ диапазона записи 1898 (переписи) выпадают.
  - **`count=50`** обязательно (50 на страницу — релевантные все на 1-й странице).
  - **Родня — СПИСКИ** (неограниченно): `adv[rel]` = list of `{first,last,exact}`; в URL повторяющиеся `spouse=…&spouse=…`. GUI: кнопки «+ Add Father/Mother/Spouse/Sibling/Child», динамические строки с ✕.
  - **Галки Exact по умолчанию ВЫКЛ** (пользователь их НЕ ставила; её правильный URL без `name_x`/`spouse_x`).
- `_build_search_url` собирает строку ВРУЧНУЮ (literal `+`; `urlencode` сломал бы `+`→`%2B`).

### Сбор результатов — СЧИТАТЬ по ИМЕНИ ЧЕЛОВЕКА, не по названию коллекции (ГЛАВНЫЙ баг)
- **БАГ, который я допустил**: ссылка в строке результата = НАЗВАНИЕ КОЛЛЕКЦИИ («1930 United States Federal Census»), а ИМЯ человека («Alexander W Sanders») — в отдельном поле строки. Я скорил по тексту ссылки → релевантные записи получали 30%, мусор (где в тексте было имя) — 90%. Сохранились 2 нерелевантные, ни одной нужной.
- **Фикс** (`_COLLECT_JS`): для каждой record-ссылки подняться к КОНТЕЙНЕРУ строки (предок с метками `Name/Spouse/Birth/Residence`), взять значение ПОСЛЕ строки-метки «Name» как имя человека, дедуп по строке, выбрать лучший record-link (`discoveryui-content/view` › `family-tree/person` › `imageviewer`). Скорить `_match_name`.
- **`_match_name` (surname-aware)**: фамилия должна совпасть **≥0.94** (SequenceMatcher) — «Sanders»=1.0 ОК, но «Saunders»≈0.93 / «Sanderson»≈0.88 / «Snyder»≈0.6 ОТВЕРГАЮТСЯ (пользователь хочет именно эту фамилию). Дедуп записей по URL между проходами (повтор под разными фильтрами = одна запись). `_clear_all_filters` — фолбэк (`button.link` «Clear all»).
- **Подкатегории/десятилетия СКРЫТЫ, пока не раскрыт родитель** (баг: на 2-м проходе «Marriage & divorce»/«1890s» не находились). `_apply_filter_click(label, parent)`: не нашёл → `_expand_parent` (клик по chevron/`aria-expanded=false` родителя) → повтор. Родитель берётся из `filters["parents"]` (строит GUI: подкатегория→категория, страна→континент, десятилетие→век). Плюс пробует вариант ±«s» («1890s»↔«1890»).
- **GUI фильтров**: `&` экранировать `&&` в тексте чекбокса (Qt ест одиночный `&` как мнемонику — метки не отображались), ключ словаря — чистый. Списки полные: Record type (категории+подкатегории), Record location (континенты + страны), Record date (десятилетия 1700s–2020s по векам).
- **Клик фильтров мной НЕ проверен живьём** (домен заблокирован) → defensive: не нашёл фильтр — лог и дальше, без падения. Сверить на живом прогоне; при поломке — перейти на URL-параметры фильтров (взять у пользователя URL после клика фильтра).

## Уроки сессии (фильтр JG, фото pamyat, GUI MH, *.JPG, 503)

### JewishGen — фильтр строго построчный
- **Поиск (search rows) ≠ фильтр (keywords).** Фамилию пользователь ИЩЕТ (уходит в форму JG), фильтр (`f1/f2/f3`) применяется к строкам результатов. Точность поиска решает сайт, не я.
- **Каждая строка результата обязана сама пройти фильтр** (`_JS_EXTRACT`): построчно, БЕЗ «семейной» группировки по тексту первого столбца (она склеивала Год/Город/Дату и тащила чужие записи — был баг с Одессой/Кишинёвом). Группировку оставил только через rowspan: ячейка-`null` (накрыта rowspan) **наследует** значение сверху, чтобы человек под растянутым «Bendery» тоже матчился.
- **OR по умолчанию.** Одно слово (город `Bendery`) → ВСЕ записи города (OR и AND одинаковы при одном слове). Несколько слов: OR = любое, AND = все в ОДНОЙ строке. **НЕ делать AND по умолчанию** — я уже обжёгся: `Bendery`+`Aron` AND дал 7 вместо 27 (пользователь ищет Арона ОТДЕЛЬНО, поэтому Одесса по «Aron» — норма, не баг).
